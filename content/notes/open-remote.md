# Open Remote: raw notes for a post

Working notes, not prose. Everything here happened on 2026-10-10, in one long Claude Code session
(plus one parallel Codex PR). Times are local (EDT). Facts are sourced from the repo, the session
transcript, and the TV itself; things that were guessed or never verified are marked.

- Repo: https://github.com/iamnbutler/open-tv-remote (public, MIT)
- App: "Open Source TV Remote" on App Store Connect, display name "Open Remote"
  - Bundle ID `com.natebutler.freeremote`, a leftover from the first name, "Free Remote – TV Control".
- Platforms: iOS 17+ / iPadOS and macOS 14+, one SwiftUI target generated by XcodeGen

---

## Why it exists

- The trigger: TV remote apps on the App Store that look free and are built to sneak in a
  subscription. Nate's reaction, verbatim: "today I learned about the absolute cancer that is tv remote
  apps fishing for in app purchases that people wont notice. $12 a WEEK."
  - That's about $624/year for an app that sends a few bytes over Wi-Fi to a TV you already own.
  - He shared 5 screenshots of the paywall flow in the first message. Worth recreating or describing in the post.
- The brief, also verbatim: "let's go build a totally free app replicating it's ability that we can
  give out for free. No in app purchases, no pay walls. Target iOS + macOS if you can."
- What "free" became over the day: no IAP, no ads, no analytics, no accounts, no third-party SDKs,
  no servers. The app talks only to devices on the local network. That rule is written into the
  repo's AGENTS.md.
- Open source came a bit later: about an hour in, it was renamed to "Open Source TV Remote" and the
  repo went public. Being open is part of the pitch: you can see it doesn't phone home.
- Personal angle that shaped features: young kids at home, so pinning Paw Patrol / Miffy for one-tap
  playback from the family's Jellyfin server became a real requirement, not a demo.
- Constraint all day: the family was using the TV. Nate's rule: "family is using the tv so don't put up any
  prompts on screen or anything right now". It became a standing rule in the repo: nothing may appear on the TV
  unless someone asked, and no keys, pairing or app launches without asking first.

## Stack and approach

- SwiftUI, `@Observable`, Swift 5 mode, one multiplatform target. The project is generated by XcodeGen, so no .xcodeproj is checked in.
- Zero dependencies. Every TV protocol is hand-written on Network.framework, Security.framework and URLSession:
  - Android TV Remote v2 (Google TV, Sony, TCL, Chromecast…): pairing on TCP 6467, remote on 6466,
    mutual TLS with a self-signed client cert, protobuf messages. Claude wrote a tiny protobuf
    reader/writer and a DER/X.509 certificate builder instead of pulling in libraries.
  - Roku ECP (HTTP), Samsung Tizen (WebSocket on 8001/8002 with a token), LG webOS (WebSocket + client key).
  - Discovery: Bonjour + SSDP + "connect and drop" TCP probes. Discovery deliberately never sends anything
    a TV would display.
- A command-line "harness" (`Tools/harness`) drives the real Android TV driver from the terminal: pair,
  connect, press keys. It was the main way to test against the TV without the app's UI.
- Debug `-demo` launch argument: a fake connected TV for screenshots and UI work without touching the real TV.
- Agents: Claude Code (Opus) did most of it. One forked Claude sub-agent built a feature in its own lane at
  the same time. Codex did PR #5 independently. GitHub's branch protection plus `lane` worktrees kept them
  out of each other's way.

## Struggles and bugs (the meat)

### 1. "I've needed to put codes in 3-4 times": pairing kept getting lost (issue #1)
- Symptom: every time another device (iPhone, Mac, a dev build) paired with the TV, the others had to
  enter a code again.
- **First diagnosis (partly right):** every install sent the TV the same client name ("Open Remote (iPhone)"), and another open-source project had hit
  the same problem (unfoldedcircle/integration-androidtv#39: "client_name needs to be unique").
  - Fix #1: tag the client name with a short hash of the device's certificate ("Open Remote (iPhone 3F2A)").
  - Also fixed: any TLS error, even a Wi-Fi blip, was treated as "the TV forgot us" and the pairing was
    thrown away. Now only real certificate rejections (`errSSLPeerBadCert`, etc.) count. On a Sony A80J a
    rejected cert shows up as -9825 after the handshake.
  - Also: Claude's own Mac debug builds kept their keys in different keychain places, so each needed its own
    code. Some of Nate's code-typing was self-inflicted by the dev process.
- **It still happened on the next TestFlight build.** Nate: "I downloded the most recet test flight and I'm still seeing it."
- **Real root cause:** the reference Python library (androidtvremote2) uses the client name as the
  certificate's Common Name. So in the other project, "make the client name unique" quietly also made
  the certificate subject unique. Our certificate's CN was the constant "FreeRemote" on every install. The
  TV appears to key pairings by certificate subject, so a unique display name alone did nothing.
  - Fix #2 (PR #9): each install generates a certificate with a random suffix in its CN.
- **Verified on the TV:** harness client A pairs, client B pairs, A reconnects with no code and succeeds.
- Not proven: Claude tried to reproduce the old failure with two clients sharing a CN. The test was set up
  wrong (the second client found and reused the first one's certificate, visible because the TV showed the
  same "Mac B2AA" ID), and it was abandoned rather than spending more pairing prompts. So the cause is
  inferred: Nate's report, plus the fix working, plus the reference library's behavior.
- Lesson for the post: the fix from someone else's bug report worked for them for a reason they didn't
  write down. Read the reference implementation, not just the issue thread.

### 2. Reading pairing codes off a TV with a laptop webcam
- The TV shows a 6-character code that has to be typed into the client, and Nate wasn't always at the TV.
- Late in the day Nate pointed Claude at a local `video-stream` skill.
  - The iPhone Continuity Camera frames came back black or blurry.
  - The MacBook Pro camera happened to face the TV across the room.
- Claude grabbed a full-res frame, read the code (9F8ECF, DA92D9, 49EEBF…), and wrote it to `/tmp/atv-code`.
  The harness polls that file. That made the whole pair → pair → reconnect test autonomous.
- Side discovery: if a client disconnects mid-pairing, the code dialog stays on the TV. Claude cleared it by
  pressing Back from an already-paired test client, then checked with another camera frame that the TV was
  back on its home screen.
- Good image for the post: the camera frame with "Device pairing request … Open Remote (Mac AA28) … 9F8ECF"
  on a Sony in a living room with toys on the shelves. Frames are at `~/.vidstream/captures/`; check what's
  in them before publishing.

### 3. Jellyfin: "spins forever" / "goes to the home page and never plays"
- Goal: tap a pinned show (Paw Patrol) on the phone and it plays on the TV's Jellyfin app.
- How it works: Jellyfin's server can tell a running client to play an item (`POST /Sessions/{id}/Playing?playCommand=PlayNow`).
- Nate's three bug reports:
  1. Jellyfin not open: spins forever on "waiting for Jellyfin".
  2. Jellyfin open: works.
  3. An episode is playing, tap another pin: the TV goes to Jellyfin's home screen and never plays.
- What Claude found in jellyfin-androidtv's source:
  - The WebSocket that receives remote commands only runs while the app is in the foreground. It's
    `repeatOnLifecycle(RESUMED)` on `ProcessLifecycleOwner`.
  - The server keeps listing the session for a while after the app goes to the background, so "a session exists"
    proves nothing.
  - Relaunching the app through the Android TV remote protocol while it's playing drops it back to its
    home screen.
  - The app ignores DisplayContent ("navigate to this item"), so there's no way to deep-link without playing.
- Our bug: the app guessed which Jellyfin session was the TV ("the only one", or "a new one after launch"). With
  other Jellyfin clients around, the guess failed. It then relaunched the app (which reset it to home) and waited
  for a session it would never recognize.
- Fix (#4):
  - Match the TV's session by IP address (`RemoteEndPoint`), sometimes IPv4-mapped IPv6.
  - Only launch the app when nothing is playing.
  - Resend PlayNow every 8 seconds until the server reports `NowPlayingItem` matching what was asked for.
  - Hard 45-second limit with a clear error.
- Launching Jellyfin uses the Android TV remote's "app link" field with `market://launch?id=org.jellyfin.androidtv`.
- Status: fix shipped to TestFlight, not yet confirmed by Nate on the TV.

### 4. App Store Connect / TestFlight / signing friction (lots of small papercuts)
- **No way to click around the web from the CLI.** Every App Store Connect step became a prompt that Nate pasted
  into the Claude in Chrome extension. The first one failed because the bundle ID had never been registered: the
  build was signed with Xcode's wildcard profile, so Apple had no record of it.
- **Xcode's login expired mid-day.** Uploads failed with "Failed to Use Accounts" while Nate was away. Builds still
  worked; only uploads need the Apple account sign-in.
- **Keychain prompts.** The unsigned test harness looked like a new program on every rebuild, so macOS kept asking
  for keychain access. Fixed by signing it with a stable identity. Nate hates the prompts, so it became a standing rule.
- **One upload was silently lost.** Piping `release.sh` through `head` killed the macOS export when the pipe
  closed, so iOS uploaded and macOS didn't. Caught by noticing there was no `export-macOS` folder.
- **iCloud sync broke local Mac builds.** The iCloud key-value entitlement needs a provisioning profile. The Mac
  development profile only listed an older Mac, so signed debug builds on this Mac failed to launch with
  POSIX error 163 ("Launchd job spawn failed").
  - `xcodebuild -allowProvisioningDeviceRegistration` didn't register the Mac.
  - Nate had to register it himself in Xcode. Quote: "I don't know where to find this signing thing in xcode".
  - Workaround for agents: build with the entitlement stripped.
- **Every TestFlight build said 1.0.** `manageAppVersionAndBuildNumber` bumped the build number but nobody bumped
  the version. Fixed forward: semver from 1.1.0, set in `project.yml`. A GitHub release tagged vX.Y.Z runs a
  workflow that uploads to TestFlight and checks the tag matches the version.
  - Open item: CI needs an App Store Connect API key with Admin access for cloud signing. It might also create
    development certificates on each run; still unproven.
- **XcodeGen quirk.** It ignored a target-level deployment target and defaulted to iOS 27, while Nate's phone
  runs 26.6. Caught on the first device install.

### 5. Things that couldn't be tested from the desk
- Volume: on the first test the TV's speaker level stayed at 8 after volume up/down. Best guess is that audio goes
  to a soundbar over HDMI-CEC. Never confirmed.
- Samsung: the Frame was there, but only Wake-on-LAN's packet format was tested, with a local listener. Notes:
  - Hold power and Wake-on-LAN are untested on the real TV.
  - iOS blocks broadcast without a special entitlement, so the phone sends the magic packet straight to the TV's IP.
  - On a Frame, a tap of power toggles Art Mode. Holding power sends a Press/Release of KEY_POWER three seconds apart.
- Roku and LG drivers were written against their documented protocols and never touched real hardware.
- Hardware volume buttons controlling the TV (#6) can't be tested in the simulator.

### 6. Process / repo things worth mentioning
- **"Never repeat anything written in code in words."** Nate's rule for docs.
  - The README lost its protocol table and folder layout.
  - `docs/` went away: the privacy policy, support and security pages became the usual top-level files, and user
    help moved to the wiki. The wiki is still waiting on Nate to create its first page; GitHub won't let the API do that.
- **Locked main.**
  - Changes need a PR, and the iOS and macOS builds must pass.
  - Squash merges only, no force pushes, and no admin bypass, so the rules apply to Nate too.
  - Secret scanning, push protection and private vulnerability reporting are on.
- **Lane worktrees and notes.** `lane` puts each task in its own worktree and keeps notes attached to code
  ("why this file is the way it is"). The notes record the non-obvious things, for example:
  - the TV seems to key pairings by certificate subject,
  - the Jellyfin app only takes PlayNow while it's in front,
  - the iCloud entitlement needs a provisioning profile.
- **CI caught the agents breaking things.** The iCloud sync refactor broke the command-line harness build, because
  the harness compiles some app files on its own. It's now built in CI.
  - The first version of that CI step also failed, because the `build/` folder didn't exist on a clean runner.
    Small, very real.
- **Squash titles.** A few PRs were opened with `gh pr create --fill`, which used the branch name. So main has

  worktrees plus required CI made that uneventful, which is itself worth a sentence.

## Feature list as of 1.1.0 (for a sidebar)
- **Remote:** D-pad, touchpad, number pad, volume, channel, media keys, power, home/back/menu/info/input/search.
- **Keyboard:** text shows on the TV as you type (Android TV, Roku, LG; Samsung sends on Enter), and the keyboard
  closes on Enter.
- **Volume buttons:** the iPhone's hardware volume buttons control the TV while the app is open.
- **Watch page** (swipe from the remote):
  - app shortcuts with real logos
  - Jellyfin continue watching and libraries
  - a poster gallery
  - series pages with "Next episode" and "Shuffle"
  - pins for kids' shows
  - now playing with controls
- **Settings:** TV setup, Jellyfin sign-in (Quick Connect), managing pins, choosing which apps show.
- **iCloud sync:** pins, app choices, the TV list and the Jellyfin sign-in. Pairing deliberately stays on each device.
- **Samsung:** hold power to turn the TV fully off, and Wake-on-LAN to turn it on.
- **TVs that change IP address** are found again by name and brand.
- **No accounts, no tracking, no network traffic** beyond the TVs and your Jellyfin server.

## Interesting things learned (quick hits)
- **Android TV pairing:** the 6-character code is mostly a secret. The client proves it saw the code by hashing
  both certificates' RSA modulus and exponent with the code. The first byte of that hash must match the code's
  first byte, which is how the TV rejects typos.
- **Android TV state:** the protocol tells the client which app is in the foreground. That's how the harness
  logged `com.spocky.projengmenu` (the Projectivy launcher) and `com.google.android.tv.remote.service` (the
  pairing dialog).
- **Jellyfin sign-in tokens** aren't tied to the device that requested them. A token synced over iCloud Keychain
  works from another device; the server just updates the device name. Checked in Jellyfin's
  `AuthorizationContext.cs`.
- **iCloud key-value storage** needs no permission prompt and doesn't count as "data collected" for the App Store
  privacy label. It's an easy win for settings sync.
- **Removed settings:** the app writes a removed setting to iCloud as empty `Data`, so "removed on another device"
  can be told apart from "never set". Otherwise a device signed out of iCloud would wipe everyone's settings, or a
  removal would come back from the dead.
- **Samsung Frame:** the power key toggles Art Mode. Turning it fully off needs a 3-second hold, the same as the
  physical remote.
